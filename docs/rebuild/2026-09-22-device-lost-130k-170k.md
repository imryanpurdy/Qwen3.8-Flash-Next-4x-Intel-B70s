# 2026-09-22 — Context ceiling: 130K prefill death, 170K DEVICE_LOST

**Artifacts:** ledger B4T-NEEDLE130, B4T-NEEDLE170; server logs; `scripts/needle_probe.py`.

## Probes (needle_probe.py, temp 0)

| Target | Result |
|---|---|
| 98,288 (98K) | PASS — `CORRECT=YES`, `STAGING_NEW=0`, prefill ~406 tok/s |
| 130K | dies **mid-prefill** — request hangs then dies; no completion |
| 170K | **DEVICE_LOST** (error-20) at PLE staging; XPU reset required |

## Why these are hard ceilings, not config

- **Positional/overflow theory excluded:** 130K fails with PLE staging NOT involved (dies before staging); 170K fails at staging. Two different death points for two different sizes.
- **Timing-based death:** the failure point moved between boots of identical config under identical load (130K passes prefill on some boots, dies on others; 170K consistently DEVICE_LOST). Timing-dependent, not deterministic-size-dependent — consistent with the XPU driver's address-space/timeout envelope at extreme sequence lengths on this stack.
- The wedge that follows a DEVICE_LOST is the sticky class: watchdog restart does not always recover the card set cleanly.

## Operating rule

**MAX_MODEL_LEN=98304 is the ceiling.** The launcher refuses anything higher (hard gate with pointer to this doc). 98K needle must PASS (`CORRECT=YES`, `STAGING_NEW=0`) after any boot serving long context.

## 3A. Official FP8 vLLM TP2 lane — /tmp/b70lab/repro/qwen38-27b-fp8-vllm-tp2-asrock-b70/

`candidate-portable-repro` on two ASRock Arc Pro B70 (32 GB each). Official `Qwen/Qwen3.8-27B-FP8` at `017b9c7a…`, **66 safetensors / 30,866,866,928 B**, image `vllm/vllm-openai-xpu@sha256:f01e24f6…`, vLLM **0.27.2rc1.dev77+gac7509e2b**, torch **2.13.0+xpu** — this is the cookbook's same `f01e24f6` generation applied to a *dual*-B70 TP2 rig.

**Headlines (all strict/single-user unless stated):**
- **Qualified strict MTP1 default (r32)**: class-balanced decode **51.919 tok/s** median (r32-A 51.607 / r32-B 52.231), 12/12 cache-zero, 12/12 repeat+target parity, exact output match vs both qualified MTP0 repeats. Build = deterministic Inductor, XPU Graph OFF, exact two-row Gemma RMSNorm replay, deterministic GDN state, explicit oneCCL `Work.wait()` completion, TF16 KV, `MAX_MODEL_LEN=1024`.
- **Qualified strict MTP0 baseline (r15)**: **34.032 tok/s** median (012/12) via deterministic-GDN + compiled-state/oneCCL patches (`VLLM_XPU_FP8_BLOCK_W8A16=1`, graph off, `CCL_P2P_ACCESS=1`); eager r5 fallback 18.910 tok/s.
- **Dynamic MTP8→MTP1 (short-ctx 256-token service)**: one user **146.8 tok/s**, c64 **1,094.3 tok/s**; MTP9 one-user 158.6 but c64 889.6 → failed retention gate (negative). The high single-user numbers come from serially reusing the checkpoint's one publisher MTP layer (8 spec tokens/request) and deliberately must not be used as a headline (audit: 128-token cap, not the 512-cap final gate).
- **W8A16 overlay**: +60.07 % single user (21.87 → **35.011**) and +29.30 % at c128 (860.5 → **1,112.6 tok/s**) on the untouched FP8 weights (activations FP16 via existing XPU W8A16 GEMM; reroutes through a lab patch; xpu.py SHA `7c36e4a8…`).
- **Exact 2K–32K one-slot W8A16 depth profile**: 35.20 → 31.49 tok/s decode across 2K→32K (TTFT 1.0–13.7 s, prompt proxies ~2.4–2.5 K tok/s); MTP1 profile matched MTP0 arrays 6/6 at 2K–32K (32K 46.64 tok/s, TTFT 10.49 s).
- **Concurrency (MTP0, 4K ctx)**: 1–64 users 21.6 → 774.4 aggregate tok/s, TTFT p50 95 ms→769 ms; legacy MTP1 concurrency: c64 **1,091.6** aggregate / 17.06 per-user.
- **Captured baseline result**: 21.71 tok/s median after TTFT (vs Q4_K_M 49.72 — vLLM official FP8 is ~2.3× slower than GGUF Q4_K_M TP2).

**Failures / rejections**: original fast MTP matrix (static MTP1 55.76, dynamic MTP8 68.05) only matched 8/12 output arrays → fixed GDN B/A prefill reduction, bounded compiled recurrent state, `async_op=True`+`Work.wait()` → repaired MTP0 to 12/12. R34–R38b repair campaign: **dynamic MTP rejected** — serial GDN made static MTP1 exact, but dynamic MTP8 still diverged at token 128 (serial packed block-FP8 pushed first sentinel to 441; batch-invariance neutral; serial FlashAttention ±causal mask regressed back to 128). TP1 control also 8/12 pre-fix → not TP2-specific. LocalMaxxing premature submission of the 58.4 tok/s screening row recommended for withdrawal.

## 3C. Known XPU failure modes — /tmp/b70lab/docs/intel-b70-minimax-feedback-20260523.md

Feedback to Intel from **MiniMax M2.7 INT4 on 4×B70** (Ubuntu 24.04, torch 2.11.0+xpu, vLLM, llm-scaler, Level Zero; the setup *worked* and passed quality gates, ~110.9 total tok/s p512/n1536). Every documented failure mode:

1. **Kernel-build memory blowup**: compiling `vllm-xpu-kernels` `paged_decode_xe2.cpp` needs **120+ GB RSS per compiler process** — 16–64 GB hosts fail without huge SSD swap; hard to distinguish slow-compile from hang. → ask for prebuilt wheels + low-RAM build mode.
2. **Version-compat is implicit**: working combo = torch 2.11.0+xpu + oneAPI 2025.3 + matching kernels source build + patched vLLM + patched llm-scaler. **Newer torch XPU nightly loaded the model but failed during vLLM torch.compile/AOT with `AssertionError: Handler already registered for <function current_stream …>`** (duplicate-handler).
3. **IGC/ocloc internal compiler errors**: at startup, Triton/Inductor emits `IGC: Internal Compiler Error: Floating point exception` / `Build failed with error code: -11` from `ocloc compile -spirv_input -device bmg`; process eventually continues but scary/ambiguous.
4. **oneAPI env mis-selection**: `setvars.sh` picks a too-new compiler stack → build trouble; directly sourcing `/opt/intel/oneapi/compiler/2025.3/env/vars.sh` works.
5. **Unknown-vLLM-env warnings hide real flags**: patched `VLLM_*` flags warn "unknown" → operators may delete working flags.
6. **Quality validation missing**: perf work on MoE/graph/allreduce/logits silently changes output quality.
7. **CPU KV offload is CUDA-only**: native path rejects XPU (`CPU Offloading is currently only supported on CUDA-alike GPUs`); local prototype moved CPU↔GPU KV at **14–16 GB/s**; blocker = XPU FlashAttention needs the active request's KV blocks live in GPU memory.
8. **Session-cache reload → Level Zero device loss**: in c4 session-cache test, copying block-table state back to GPU hit `RuntimeError: level_zero backend failed with error: 20 (UR_RESULT_ERROR_DEVICE_LOST)` in `gpu_model_runner._prepare_inputs → block_table.commit_block_table → copy_to_gpu` under scheduler pressure.
9. **TurboQuant workspace lock**: XPU first run failed `Workspace is locked but allocation from turboquant_attn.py:_decode_attention requires 0.19 MB, current size is 0.00 MB`; local fallback (temp buffers when workspace locked) let `turboquant_k8v4` start at 32K (~80,128 GPU KV tokens) but sustained decode much slower than FP16 KV.
10. **NaN logprobs break JSON**: long-context logprob checks fail `Out of range float values are not JSON compliant: nan`.

Also (cross-lane context from cookbook/RELIABILITY-REPORT): `vllm-xpu-kernels` prebuilt wheel ABI mismatch (`undefined torch Library::_def` symbol); the Xe2 wedge (2–6 h under sustained multi-GPU load — `xe` engine reset, `Fault response: Unsuccessful -ENOENT/-EINVAL`, `EngineDeadError`, container restart only); multi-device L0 V2 context creation `UR_RESULT_ERROR_UNKNOWN`; oneCCL `zeMemOpenIpcHandle ZE_RESULT_ERROR_INVALID_ARGUMENT` on non-P2P boards; PyTorch XPU enum = 0 devices on fresh builds.

## 3D. Community lanes

### SergiioB Qwen3.8-27B vLLM-XPU — /tmp/b70lab/community/sergiiob-qwen38-27b-vllm-xpu/
The cookbook author's **single-B70 GPTQ-INT4 route**, captured at cookbook commit `3beb704b…` (model `SergiioB/Qwen3.8-27B-GPTQ-Int4-sym-G128-MTP-BF16` @ `9d189a60…`, 18.2 GiB, 15 `mtp.*` tensors verified BF16 on disk, image f01e24f6). Evidence level `B70-tested/performance; quality-rejected as no-loss default; community-reported for 131K/power`.
- **Achieved (independent 8K lab repro, p512/g128 n=5)**: target-only XPU-graph 33.69 vs 25.42 eager tok/s; **MTP1 54.18 / MTP2 68.23 / MTP4 83.70 tok/s** — MTP4 matches the contributor's 83.7 claim; all four modes byte-identical greedy outputs (5 shared hashes). Native FP16 KV: 34.16 target-only / 87.61 MTP4. **Patch A/B**: with the Qwen MTP patches active vs not, MTP4 = 83.70 vs 83.70 (−0.006 %) → the nightly MTP patch is **redundant for this pinned model at 8K**; the 131K boundary patch untested.
- **Failed / rejected**: a wider semantic canary found a real **GPTQ target error — arithmetic `30` instead of `14`** — while Q8/Q4 GGUF passed; so the packet is explicitly NOT the no-quality-loss deployment. Long-context, power, and contributor-prompt identities unresolved. Artifact audit also flagged the second contributed URL as unrelated (a web-app spec). Both copied patchers verified apply/idempotent on the pinned image; a low-memory download lesson (2 GiB container exit-137 on 8 concurrent Xet transfers).

### bosd TRX50 2×B70 field reports — /tmp/b70lab/community/field-reports/bosd/trx50-2xb70/
Nine+ community-reported pages; `qwen38-27b-mtp.md` headline: **Qwen3.8-27B MTP works out-of-the-box on Intel vLLM-XPU (one B70)** — intel/llm-scaler b3.1 image (vLLM 0.21.1.dev0+gad7125a43, torch 2.11.0+xpu, podman), online `sym_int4`, `qwen3_5_mtp` spec n=2: **MTP-off 28.9 → MTP-on 44.9 tok/s (+55 %)**, ~61 % accept (lower than Qwen3.6-27B's 74 %/+80 % → consistent with untuned newer checkpoint; draft head shares weights). Maintainer (2026-08-17) verified the image supports `qwen3_5_mtp` and the +55 % arithmetic, but not from raw logs; noted `CCL_ZE_IPC_EXCHANGE=sockets` is not by itself proof of a P2P defect.
- **TP2 follow-up (their stack)**: with `CCL_ZE_IPC_EXCHANGE=sockets` + util 0.80/MBT 4096, tp2 now runs through engine warmup (~37 s, 9.12 GiB/card) but **APIServer↔EngineCore handshake stalls after warmup** (no "startup complete", HTTP never serves) — read as a tp>1 front-end bug in b3.1; llama.cpp `-sm layer` SIGABRTs immediately (ggml#23797).
- **Maintainer audit of PRs #30–#33**: #31 image/checkpoint support verified but +55 % stays community-reported; #32's "b3.1 lacks an XPU quantized-MoE kernel" claim **corrected** (the image does contain XPU INT4 fused-MoE classes; `sym_int4` is Intel's documented path for Qwen3.5/3.6 MoE); #33 (Q4_K_M + Q4_0 draft-MTP, TP2, llama.cpp) reproduced with the lab's same-family binary: **MTP8 full-response was 10.2 % BELOW matched target-only** (46.23 vs 48.82 tok/s; first-100 ranged 34.3–81.1, mean accept 0.259) — the contributed 84–97 tok/s came from a prompt-selected favorable row and did **not generalize**. No functional quality failure found (7 canaries + 3,829-token needle passed). This audit's target-only 48.82 tok/s is the same lineage as the q4km TP2 repro record.
